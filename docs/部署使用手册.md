# 部署与使用手册

> 适用对象：第一次接触本平台、对 Kubernetes / 容器 / 工作流不太熟悉的同学。
> 目标：照着做，就能把平台跑起来，并跑通第一个实验。

---

## 0. 这东西是干嘛的？

一句话：**它是一个"在 Kubernetes 上跑一堆仿真微服务，然后用工作流串起实验（注入故障、跑算法、看结果）"的沙箱**。

- 想研究三个课题：**故障感知**（怎么发现服务挂了）、**容错**（挂了怎么兜底）、**一致性**（分布式状态怎么保持一致）。
- 平台已经帮你把 17 个微服务、链路追踪（Jaeger）、监控（Prometheus）、K8S 治理（限流/配额/自愈）都搭好了。
- 你大部分时间只需要：改一个 YAML 实验配置 → 跑一条命令 → 看结果。

几个会出现的词：
| 词 | 大白话解释 |
| --- | --- |
| K3S | 一个"迷你版 Kubernetes"，用来管容器（微服务）。本平台就跑在单节点 K3S 上 |
| 微服务 / Pod | 一个微服务 = 一个独立小程序，跑在 K3S 里叫一个 Pod |
| 命名空间 `sim-test` | 把所有实验相关资源圈在一个"隔离区"里，避免干扰别的业务 |
| 工作流 `wf.py` | 一个 Python 小引擎，按 YAML 顺序执行"步骤"，每步调用一个"动作" |
| 动作 actions | 可复用的操作（查健康、注入故障、采 trace、跑算法…） |
| 算法 algos | 你真正要研究的逻辑（故障感知/容错/一致性）放在这里 |
| 镜像 image | 微服务的"安装包"，用 buildah 构建后装进 K3S |

## 2. 第一步：进入代码目录、装 Python 依赖

```bash
# 1) 远程登录（你本地用 ssh 客户端连 192.168.1.202）
ssh root@192.168.1.202     # 密码 darren

# 2) 进入项目目录
cd /mnt/hgfs/code/sim_lab

# 3) 安装 wf.py 运行所需的 Python 包（只需要两个：pyyaml、kubernetes）
python3 -m pip install -i https://mirrors.aliyun.com/pypi/simple -r requirements.txt
```

如果提示 `kubectl` / `k3s` 不存在，说明这台机器还没装 K3S。安装命令（全新机器才需要）：
```bash
curl -sfL https://get.k3s.io | sh -          # 装完会自动起一个单节点 K3S
sudo k3s kubectl get nodes                   # 能看到 ubu-22 Ready 就成功了
```
本机已装好，跳过即可。

## 3. 第二步：构建并导入 17 个微服务镜像

平台有 17 个微服务（11 个核心仿真 + 6 个通用平台）。首次需要把它们"打包成镜像"并塞进 K3S。
脚本会构建：`orchestrator, scenario-mgr, entity-service, comms-service, sensor-service, fire-control, env-service, log-service, state-store, telemetry-gw, sim-bridge` + `api-gateway, auth-service, config-service, notification-service, platform-service, chaos-service`。

```bash
# 安装构建工具（若没有）
sudo apt-get install -y buildah

# 一键构建 17 个镜像并导入 K3S（约几分钟，需联网）
sudo ./scripts/build-images.sh
```

可选用法：
```bash
sudo ./scripts/build-images.sh fire-control     # 只重建某一个服务
IMPORT=0 sudo ./scripts/build-images.sh         # 只构建不导入（CI 用）
```

> ⚠️ 注意：`sim-bridge` 镜像在构建时会**联网下载 ROSS 8.1.1 源码并编译**进镜像。
> 如果构建机不能访问 GitHub，这一步会失败——需要在能联网的机器上构建，或提前备好 ROSS 源码。

构建完成后可确认镜像已在 K3S 里：
```bash
sudo k3s crictl images | grep 'docker.io/sim/'
```

## 4. 第三步：部署到 K3S

```bash
./scripts/deploy.sh
```

这个脚本会按顺序做这些事（顺序很重要，不要手改）：
1. 创建命名空间 `sim-test`
2. 部署 10 个核心服务（all-services.yaml）+ fire-control + 11 个 Service
3. 部署平台服务 RBAC / 6 个平台服务 / 治理策略（配额·PDB·HPA）/ Ingress
4. 部署可观测性组件 Jaeger、Prometheus
5. 滚动重启所有 Deployment 以加载最新镜像
6. 等待全部 Pod 进入 `Ready`

看到末尾打印出 `get pods -o wide` 且所有 Pod 都是 `1/1 Running` 即成功。

部署顺序对照（与 `docs/K3S-PLATFORM.md` 一致）：
```
namespace → all-services → fire-control → services
→ platform-rbac → platform-services → platform-policy → platform-ingress
→ jaeger → prometheus
```

## 5. 第四步：验证平台是否真的能跑（最关键）

平台自带一个"只读 + 一次良性业务触发"的自检脚本。**它能跑过，就说明平台是活的。**

```bash
./scripts/verify_platform.sh
```

你应当看到类似结尾：
```
== 追踪与指标 ==
  [PASS] Jaeger API 可用: {"ok": true, "services": 18}
  [PASS] Prometheus targets: {"ok": true, "up": 17, "total": 17}
== K3S 平台治理对象 ==
  [PASS] hpa: 1 个
  [PASS] pdb: 2 个
  [PASS] resourcequota: 1 个
  [PASS] limitrange: 1 个
  [PASS] ingress: 1 个
== chaos-service RBAC 自检 ==
  [PASS] chaos-service 可读取 Pod（RBAC 生效）

========== 结果: PASS=58 FAIL=0 ==========
```

**实测结果：PASS=58 FAIL=0。**

自检会检查：节点/Pod/Deployment 就绪、18 个 Service 端点、`state-store` 三副本一致性、`/trigger` 业务链路返回 `engaged`、Jaeger/Prometheus 可用、HPA/PDB/配额/Ingress 对象存在、chaos-service 最小权限 RBAC。

> 如果 Jaeger/Prometheus 没部署，对应项会显示 `INFO 跳过`，不会算 FAIL。

## 6. 第五步：跑你的第一个实验（工作流）

实验由 `configs/*.yaml` 描述，`wf.py` 负责执行。先看最简单的链路追踪实验：

```bash
python3 wf.py run --config configs/tracing_pipeline.yaml --id trace-001
```

你会看到每一步的实时日志：
```
[RUN] check_env: 检查微服务与 Jaeger 状态
[OK] check_env completed in 0.09s
[RUN] traffic: 发起真实业务流量（产生跨服务调用链）
[TRAFFIC] requests=6 engaged=6 degraded_or_failed=0
[OK] traffic completed in 2.21s
[RUN] trace: 从 Jaeger 采集真实 Trace 并聚合...
[TRACE] traces=235 spans=501 edges=16 coverage=1.0
...
Workflow completed: trace-001
```

这就证明：11 个服务都活着 → 发了 6 次真实业务请求都成功 → Jaeger 里真采到了 235 条 trace、501 个 span → 运行态依赖图和设计一致 → 落库校验通过。

### 6.1 常用实验命令

| 目的 | 命令 |
| --- | --- |
| 故障感知（深度学习 + 真实 trace） | `python3 wf.py run --config configs/algo_samples.yaml --id algo-001` |
| 基线故障感知（K8S 就绪探针） | `python3 wf.py run --config configs/military_fault_detect.yaml --id detect-001` |
| 容错 | `python3 wf.py run --config configs/military_fault_tolerate.yaml --id tol-001` |
| 状态一致性（真实 netem + 分叉 + 修复） | `python3 wf.py run --config configs/military_consistency.yaml --id consist-001` |
| 链路追踪验证 | `python3 wf.py run --config configs/tracing_pipeline.yaml --id trace-001` |
| A/B 对比（基线 vs 追踪） | `python3 wf.py run --config configs/ab_trace.yaml --id ab-001` |

### 6.2 单步调试 / 断点续跑 / 跳步（调试算法时极有用）

```bash
# 只跑某一步（例如只跑检测算法，方便反复改 algo 代码）
python3 wf.py run --config configs/military_fault_detect.yaml --id test-002 --step detect

# 从上次失败的某一步继续（之前的步骤标记为 SKIPPED，不重跑）
python3 wf.py run --config configs/military_fault_detect.yaml --id test-001 --from detect

# 跳过某些步骤
python3 wf.py run --config configs/military_fault_detect.yaml --id test-001 --skip baseline,cleanup
```

### 6.3 查看实验状态与结果

```bash
python3 wf.py status --id trace-001
```
每次实验的输出在 `runs/<实验ID>/` 下：
- `state.json`：每步的状态、耗时、错误
- `ctx.json`：完整上下文（注入时刻、故障信息、网络规则等），用于断点续跑
- `trace_stats.json` / `trace_graph.json`：追踪统计与依赖图

## 7. 看观测面板（Jaeger / Prometheus）

### Jaeger（看真实调用链 / 定位故障服务）
```bash
kubectl -n sim-test port-forward svc/jaeger 16686:16686
```
浏览器打开 http://localhost:16686 → 服务选 `orchestrator`，按 `peer.service` 排序即可看到哪个下游被调用失败。

### Prometheus（看指标）
```bash
kubectl -n sim-test port-forward svc/prometheus 9090:9090
```
浏览器打开 http://localhost:9090，输入指标名（如 `orchestrator_requests_total`）查询。

### 通过 Ingress 从集群外访问网关
```bash
# 方式一：hosts 指向节点 IP
echo "<节点IP> sim-lab.local" | sudo tee -a /etc/hosts
curl http://sim-lab.local/gateway/health

# 方式二：端口转发（不依赖 hosts）
kubectl -n sim-test port-forward svc/api-gateway 8088:8080
curl http://127.0.0.1:8088/gateway/health
```

## 9. 常见问题与排错

| 现象 | 原因 | 解决办法 |
| --- | --- | --- |
| `ImagePullBackOff` | 镜像没导入 K3S，或 tag 不对 | 先 `sudo ./scripts/build-images.sh`；确认 `imagePullPolicy: IfNotPresent` |
| `verify_platform.sh` 部分 FAIL | 服务没起来 / 网络问题 | `kubectl -n sim-test get pods` 看哪个没 Ready；看日志 `kubectl -n sim-test logs deploy/<服务>` |
| `/trigger` 返回非 `engaged` | 某下游不健康 | 查 Jaeger 看 `peer.service` 失败的那个服务 |
| `fault.inject_netem` 不生效 | 不是 root / 宿主机缺 `tc`/`nsenter` | 用 root 跑 `wf.py`；确认 `tc`、`nsenter`、`k3s crictl` 存在 |
| 构建 `sim-bridge` 卡在下载 ROSS | 构建机无法访问 GitHub | 换可联网机器构建，或预置 ROSS 源码 |
| 改了 `services/common/*` 没生效 | 镜像没重建 | `sudo ./scripts/build-images.sh <服务>` 重建 → `./scripts/deploy.sh` 滚动更新 |
| Python 报 `ModuleNotFoundError: yaml` | 没装依赖 | 回到第 2 步重装 `requirements.txt` |

## 10. 已知限制（别踩坑）

1. **单节点集群**：HPA/PDB 的对象与策略"存在且正确"，但没有多节点调度/节点故障转移可演示。
2. **NetworkPolicy 依赖 CNI**：K3S 默认 flannel 不强制网络隔离。`fault.inject_network_partition` 会创建策略对象，但隔离效果取决于 CNI；需要确定性隔离请用 `fault.inject_netem`（真实生效，需 root）。
3. **netem 需要宿主机权限**：容器内做不了，动作放在 wf.py 运行的主机侧。
4. **检测仍是批处理**：一次算法扫描约 10 秒，不是流式检测。
5. **存储非持久**：Jaeger 内存存储（2 万条上限）、Prometheus `emptyDir`，Pod 重建即清空。
6. **镜像为本地导入**：`:latest` 必须配 `IfNotPresent`；重建镜像后要重启 Deployment 才加载新镜像。
7. **单副本平台服务**：auth/config/notification/platform/chaos 仍是单副本；它们故障只短时影响对应能力，不影响核心仿真链路。

> 结论：这是一个**算法研发与验证沙箱**，适合做故障感知/容错/一致性研究，**不要直接当生产高可用平台用**。
