## 2. 核心概念：四层模型

平台是一个四层架构（详见 `docs/ARCHITECTURE.md`）：

```
实验层    configs/*.yaml        想定/故障/算法/测量/清理 的"实验剧本"
   ↓ python3 wf.py run
编排层    wf.py                 步骤状态机、变量解析、超时、断点续跑、上下文落盘
   ↓ 调用 actions.* / algos.*
动作层    actions/               k8s/fault/obs/trace/state/ross/measure（复用操作）
算法层    algos/                fault_detect_* / fault_tolerate_* / consist_*
   ↓ 操作 K8S / Jaeger / Prometheus
运行层    K3S 命名空间 sim-test  17 微服务 + Jaeger + Prometheus + Traefik(Ingress)
```

## 3. wf.py 详解（最重要的一份代码）

`wf.py` 是一个**自研的简单工作流引擎**，约 385 行，零第三方框架依赖（只用 `yaml`、`argparse`）。

### 3.1 动作注册机制（怎么把动作"挂"上去）
```python
ACTIONS = {}                       # 全局动作字典

def register_action(name):         # 装饰器
    def decorator(fn):
        ACTIONS[name] = fn         # 把函数登记到字典，key 是动作名
        return fn
    return decorator

# 在 actions/*.py 里这样用：
@register_action("k8s.check_ready")
def check_ready(ctx, params): ...
```
`wf.py` 的 `main()` 开头统一 `import actions.k8s / fault / obs / algo / measure / ross / trace / state`，
把这些模块里的装饰器全部触发，于是 8 个文件里的所有动作都进了 `ACTIONS` 字典。
配置里写的 `action: k8s.check_ready` 就是来这里查表的。

> 提醒：新增动作只要 
> (1) 在 `actions/` 下新建文件写 `@register_action("xxx.yyy")`，
> (2) 在 `wf.py` 的 `main()` 里加一行 `import actions.你的文件`。配置里就能引用了。

### 3.2 一次运行的生命周期
1. `WorkflowEngine.__init__`：读 YAML → 建 `runs/<id>/` → 初始化 `ctx`（上下文）→ 加载/新建 `state.json`、`ctx.json`。
2. `run()`：先做 `_validate_steps`（校验每个 step 有 id/name/action 且不重复）→ 顺序执行。
3. 每个 `run_step()`：
   - 已 SUCCEEDED 且非 `always_run` → 跳过；
   - 否则查 `ACTIONS[action_name]`，用 `resolve_vars()` 把参数里的 `${vars.xxx}` 替换成真实值；
   - 用 `_run_with_timeout()`（Linux `SIGALRM` 信号）给单步加超时兜底；
   - 成功写 `SUCCEEDED`+耗时，失败写 `FAILED`+错误；结果 `_jsonable()` 后落盘。
4. `always_run`（如 cleanup 清理步骤）即使前面失败也会执行。

### 3.3 三个对极有用的能力
| 能力 | 命令行 | 原理 |
| --- | --- | --- |
| 单步调试 | `--step detect` | 只跑指定 id 的一步 |
| 断点续跑 | `--from detect` | 之前未成功的步骤标 `SKIPPED`，从指定步继续（ctx.json 保住注入时刻等） |
| 跳过步骤 | `--skip a,b` | 跳过指定 id |

### 3.4 上下文 `ctx` 是贯穿全程的"记事本"
`ctx` 存实验 ID、配置、变量、时间戳、注入时刻、故障信息、网络规则等。
每步结束都 `save_ctx()` 落盘到 `runs/<id>/ctx.json`，所以中途断了也能接着跑、且计时口径一致。

## 4. actions/ 动作层（可复用的操作步骤）

每个 `.py` 文件是一组相关动作，文件名即前缀：

| 文件 | 动作前缀 | 干什么 |
| --- | --- | --- |
| `k8s.py` | `k8s.*` | 检查服务就绪、查端点等集群操作 |
| `fault.py` | `fault.*` | 故障注入：`inject_pod_kill`（删 Pod）、`inject_netem`（宿主机 tc 注入延迟/丢包）、`inject_network_partition`（NetworkPolicy） |
| `obs.py` | `obs.*` / `traffic.*` | 观测基线采集、`traffic.probe` 打真实业务流量 |
| `algo.py` | `algo.*` | 加载并调用 `algos/` 里的算法（`run_detect` / `run_tolerate` / `run_consist`） |
| `measure.py` | `measure.*` | 测量：`detect_latency`（证据延迟/扫描耗时）、`recovery_time`、`summary` |
| `ross.py` | `ross.*` | 通过 `kubectl exec` 调 sim-bridge 的 `/start`/`/status` 跑真实 ROSS |
| `trace.py` | `trace.*` | `collect`（聚合服务级指标+运行态依赖图）、`graph`（对比设计态）、`verify`（校验落库）、`traffic.probe` 也常归这里 |
| `state.py` | `state.*` | state-store 副本操作：`reset`/`write`/`verify`（查分叉）/`repair`（反熵修复） |

> 注意：动作层是"操作"，算法层是"决策"。动作负责"注入故障、采数据"，算法负责"看到数据后判断根因/怎么容错"。

## 5. algos/ 算法层（真正要研究的东西）

统一接口（详见 `algos/_template.py`）：
```python
def detect(ctx):  ...   # 故障感知：返回是否检出、根因服务、置信度、证据延迟
def tolerate(ctx): ...  # 容错：返回降级/调度决策
def consist(ctx): ...   # 一致性：返回模糊-排队协同决策
```

现有实现：
| 文件 | 类别 | 说明 |
| --- | --- | --- |
| `fault_detect_baseline.py` | 感知-基线 | 基于 K8S 就绪探针，最快但依赖自愈相位 |
| `fault_detect_dl.py` | 感知-深度学习 | 基于真实 trace + 指标，PCA/AutoEncoder 评分 + 贝叶斯根因排序 |
| `fault_tolerate_baseline.py` | 容错-基线 | 服务降级/重调度 |
| `fault_tolerate_rl.py` | 容错-强化学习 | 用 RL 做动态调度 |
| `consist_baseline.py` | 一致性-基线 | 简单副本同步策略 |
| `consist_fuzzy_queue.py` | 一致性-模糊排队 | 模糊控制 + 排队论协同决策（实验里实测会进入 TRIGGERED 强同步） |
| `_template.py` | 模板 | 新建算法时复制它 |

**怎么加一个新算法**（三步）：
1. 复制 `algos/_template.py` 为 `algos/my_detect.py`，实现 `detect(ctx)` 返回字典；
2. 在实验 YAML 里写：
   ```yaml
   - id: detect
     action: algo.run_detect
     params:
       algo: my_detect        # 对应 algos/my_detect.py
   ```
3. `python3 wf.py run --config 你的.yaml --id xxx`

## 6. configs/ 实验配置（YAML 剧本格式）

7 个现成配置：
`ab_baseline.yaml` `ab_trace.yaml` `algo_samples.yaml` `military_consistency.yaml`
`military_fault_detect.yaml` `military_fault_tolerate.yaml` `tracing_pipeline.yaml`

一个配置长这样（以 `tracing_pipeline.yaml` 为例）：
```yaml
name: 链路追踪验证（Jaeger 真实 Trace）
namespace: sim-test
vars:
  probe_requests: 6          # 自定义变量
  trace_lookback_s: 900
steps:
  - id: check_env
    name: 检查微服务与 Jaeger 状态
    action: k8s.check_ready  # 对应 actions/k8s.py 里的 check_ready
    params:
      services: ["orchestrator", "scenario-mgr", ... "sim-bridge"]
    timeout: 60
  - id: traffic
    action: traffic.probe
    params:
      requests: "${vars.probe_requests}"   # 引用上面 vars 的变量
      interval_s: 0.2
    timeout: 120
  - id: trace
    action: trace.collect
    params: { lookback_s: "${vars.trace_lookback_s}", limit: 120 }
    timeout: 120
  - id: graph
    action: trace.graph
    timeout: 60
  - id: verify
    action: trace.verify
    params: { lookback_s: "${vars.trace_lookback_s}" }
    timeout: 60
```
**字段含义**：`id`(步骤唯一标识) / `name`(给人看) / `action`(调哪个动作) / `params`(参数，支持 `${vars.x}`) / `timeout`(秒) / `record_time`(把本步开始时间记进 ctx，如 inject_time) / `always_run`(失败也跑，用于清理)。

## 7. services/ 微服务层

### 7.1 共享底座 `services/common/`
- `base.py`：`create_app()` 工厂函数。每个服务都调用它，自动获得：
  - `GET /healthz`（存活）、`GET /readyz/business`（业务就绪）
  - `GET /metrics`（Prometheus 指标，服务名里的 `-` 会自动规范成 `_`）
  - `GET /tracez`（追踪自检）
  - ASGI 中间件：每个入站请求自动生成 SERVER span，经 OTLP/HTTP JSON 发往 Jaeger
- `tracing.py`：纯标准库实现的追踪 SDK（W3C `traceparent` 传播、span 上报），**无第三方依赖**。

### 7.2 11 个核心仿真服务
| 服务 | 职责 | 主要下游 |
| --- | --- | --- |
| `orchestrator` | 业务编排入口，`POST /trigger` 串起完整作战链路 | 全部核心服务 |
| `scenario-mgr` | 想定加载、任务状态 | state-store、log-service |
| `entity-service` | 作战实体/单位数据 | — |
| `comms-service` | 通信指令下发 | — |
| `sensor-service` | 目标航迹/情报融合 | entity-service、env-service |
| `fire-control` | 火控交战（核心） | sensor-service、comms-service |
| `env-service` | 地形气象 | — |
| `log-service` | 日志（可降级） | — |
| `state-store` | 可复制状态存储（3 副本，一致性实验对象） | 副本间反熵 |
| `telemetry-gw` | 遥测落库 | — |
| `sim-bridge` | ROSS 仿真引擎桥接（真实 mil_sim） | ROSS 子进程 |

### 7.3 6 个通用平台服务
| 服务 | 职责 | 关键接口 |
| --- | --- | --- |
| `api-gateway` | 统一入口、健康聚合、受限反向代理、令牌转发 | `/gateway/health`、`/gateway/proxy`、`/gateway/token` |
| `auth-service` | HMAC-SHA256 无状态令牌签发/校验 | `/auth/token`、`/auth/verify`、`/auth/policy` |
| `config-service` | 版本化配置中心 | `/config`、`/config/{key}`、`/config-history` |
| `notification-service` | 分级通知缓存与统计 | `/notify`、`/notifications`、`/notify/stats` |
| `platform-service` | 节点/Pod 身份、cgroup 限额、组件健康 | `/platform/info`、`/platform/health`、`/platform/capabilities` |
| `chaos-service` | 集群内 Pod kill / Deployment 伸缩（最小权限 RBAC） | `/chaos/pod-kill`、`/chaos/scale`、`/chaos/self-check` |

每个服务目录结构一致：`app.py` + `Dockerfile` + `requirements.txt`（注意：服务自己的 `requirements.txt` 含 FastAPI 等，与根目录的 `requirements.txt` 不同）。

### 7.4 入口长什么样（orchestrator 的 /trigger）
`POST /trigger` 会：先逐个 `healthz` 探测 10 个下游 → 调 `scenario-mgr` 加载想定 → 调 `fire-control/engage`（火控内部再调 sensor/env）→ 调 `telemetry-gw/ingest` 落库。每一次下游调用都带 `traceparent`，所以在 Jaeger 里是一条 15+ span 的完整链路。本次实测该链路健康下游 10 个、返回 `engaged`。

## 8. manifests/ K8S 清单（怎么把服务变成容器）

10 个 YAML，部署顺序由 `scripts/deploy.sh` 固定：
```
namespace.yaml         命名空间 sim-test（隔离边界）
all-services.yaml      10 个核心 Deployment（fire-control 单独拆出）
fire-control.yaml      fire-control Deployment + Service（P0 核心独立配额）
services.yaml          11 个 ClusterIP Service + state-store-headless（无头服务，暴露 3 副本 IP）
platform-rbac.yaml     ServiceAccount/Role/RoleBinding（chaos-service 最小权限）
platform-services.yaml 6 个平台服务 + Secret
platform-policy.yaml   LimitRange / ResourceQuota / 2×PDB / HPA
platform-ingress.yaml  Ingress（Traefik）
jaeger.yaml            Jaeger 追踪后端
prometheus.yaml        Prometheus 指标采集（ConfigMap 是唯一配置源）
```
> 数量核对：Deployment 共 **19** = 10(all) +1(fire-control) +6(platform) +1(jaeger) +1(prometheus)；
> 注意 `platform-policy.yaml` 里出现的 `kind: Deployment` 是 HPA 的 `scaleTargetRef` 引用（指向 api-gateway），**不是**独立 Deployment 对象。

## 9. ross-sim/ ROSS 仿真（C 语言，研究底座）

- `CMakeLists.txt` + `include/mil_sim.h` + `src/*.c`（comm_lp / events / fire_control_lp / main / sensor_lp / terrain_lp / unit_lp）：这是一个 ROSS 8.1.1 的离散事件仿真想定（LP = 逻辑进程）。
- `scripts/build.sh` `scripts/run_scenario.sh`：本地编译/运行入口。
- **它不会单独部署成服务**：`services/sim-bridge/Dockerfile` 用多阶段构建，在镜像内下载并编译 ROSS + ross-sim，运行时 `sim-bridge` 通过 `/start` 调起真实 `mil_sim` 子进程（实测 `mode=real, returncode=0`）。
- 这让"容错/一致性实验"能真正驱动底层离散事件仿真，而不是用假数据凑数。

## 10. 一次实验从 YAML 到结果的数据流（以故障感知为例）

```
configs/algo_samples.yaml
   ↓ python3 wf.py run
wf.py: 载入 → 逐步执行
   ├─ obs.collect_baseline   采集 metrics-server + Prometheus 基线
   ├─ traffic.probe          在 orchestrator Pod 内发真实 /trigger
   ├─ fault.inject_pod_kill  删除 fire-control Pod，记 inject_time 到 ctx
   ├─ traffic.probe          故障期继续打流量 → 产生失败 span
   ├─ algo.run_detect        调 algos/fault_detect_dl.py：查 Jaeger(窗口从注入前2s起)→ PCA/AutoEncoder 评分 → 贝叶斯根因排序
   ├─ measure.detect_latency 输出证据延迟/扫描耗时（负值钳到 0 并标 anomaly）
   ├─ trace.collect          落盘 trace_stats.json / trace_graph.json
   ├─ algo.run_tolerate / measure.recovery_time  容错与恢复时间
   └─ measure.summary        汇总三项研究 + 状态一致性校验
结果写入 runs/<id>/state.json + ctx.json
```
实测一次故障感知：根因定位 `fire-control`（置信度 0.977），证据延迟 +0.9346s，扫描 10.1s，端到端 17.35s —— **都是真实数据**。

## 11. 怎么扩展（加东西的通用方法）

| 想加什么 | 怎么做 |
| --- | --- |
| 新算法 | 复制 `algos/_template.py` → 实现 `detect/tolerate/consist` → 在 YAML 的 `algo.run_*` 参数引用文件名 |
| 新动作 | 在 `actions/` 新建文件写 `@register_action("x.y")`，并在 `wf.py` 的 `main()` 加 `import actions.x` |
| 新微服务 | 复制 `services/config-service/` 的 `Dockerfile`+`requirements.txt`+`app.py`；用 `create_app()`；在 `manifests` 加 Deployment+Service；在 `build-images.sh` 和 `deploy.sh` 的 `SERVICES` 登记；如需网关访问把服务名加进 `api-gateway` 的 `ALLOWED` |
| 改了 common 代码 | 必须 `sudo ./scripts/build-images.sh <服务>` 重建镜像 → `./scripts/deploy.sh` 滚动更新（**没有热补丁脚本**） |
